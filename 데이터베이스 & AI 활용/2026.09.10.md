## 동시성 제어 — 비관적 락 vs 낙관적 락

### 비관적 락 (Pessimistic Lock)
- 여러 사람이 동시에 같은 데이터를 수정하려고 할 때, 미리 잠그고 시작
- ex) 화장실 문을 먼저 잠그고 들어가는 것과 같다

| 장점 | 단점 |
|---|---|
| 충돌이 아예 안 일어남 (100% 안전) | 다른 사람들이 계속 기다려야 함 (느림) |
| 데이터 정합성 확실히 보장 | 사용자 많으면 병목현상, 성능 저하 |

### 낙관적 락 (Optimistic Lock)
- "설마 동시에 건드리겠어?" 하고 일단 각자 처리한 다음, 나중에 충돌났는지만 확인

**동작 방식**
- 테이블에 `version`이라는 숫자 컬럼을 하나 둠
- 미리 막는 게 아니라, 내가 본 데이터 버전이 아직 그대로인지 나중에 확인하고 바뀌었으면 그때 튕겨냄
- ex) 화장실 문을 안 잠그고 그냥 씀. 나갈 때 "아까 들어갔을 때랑 지금 상태가 같나?" 확인해서, 누가 이미 다녀갔으면 "어, 뭔가 바뀌었네, 다시 해야겠다"라고 처리하는 것

| 장점 | 단점 |
|---|---|
| 다른 사람을 기다리게 안 함 (빠름) | 충돌 나면 재시도해야 함 (실패 처리 필요) |
| 동시 접속 많아도 성능 좋음 | 충돌이 잦으면 오히려 비효율적 |

> 충돌이 잦을 걸로 예상되면 비관적 락, 충돌이 드물 걸로 예상되면 낙관적 락

## Supabase — RLS (Row Level Security)
- 로그인한 사용자는 자기 데이터만 볼 수 있도록 DB 단에서 권한을 체크하는 기능
- CRUD 각 작업마다 "이 요청을 보낸 사용자가 이 행에 접근할 자격이 있는가"를 DB가 직접 검증
- 애플리케이션 코드에서 일일이 권한 체크를 하지 않아도, DB 레벨에서 원천 차단됨
